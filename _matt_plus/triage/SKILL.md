Move issues on the project tracker through a small state machine of triage roles. `[YOU]` is this thread, the orchestrator: you run every phase, and no phase here is worth a dispatch — the maintainer's direction belongs in the same thread as the notes.

Invocation: `/skill:triage <what the maintainer wants, in natural language>` — "show me what needs attention", "look at #42", "move #42 to ready-for-agent", "what's ready for agents?". Invoking authorises reading the tracker and the codebase, running the project's own checks, and writing labels, comments, and closes to the tracker.

A named state is an instruction, not a proposal: "move #42 to ready-for-agent" skips Phases 3 to 5. Confirm the concrete actions first — role changes, comment, close — then take them. Moving to `ready-for-agent` without a grilling session raises one question: do they want an agent brief written?

The tracker setup and the label mapping should have been provided to you. If not, tell the user to run `/setup-matt-pocock-skills`.

## Roles: five **state**, two **category**

- `needs-triage`: a maintainer must evaluate it
- `needs-info`: waiting on the reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

Category roles: `bug` (something is broken) and `enhancement` (new feature or improvement).

Every triaged item carries exactly one category role and exactly one state role. Conflicting state roles: flag them and ask the maintainer before anything else. An item whose state you cannot name is the failure this skill exists to prevent; these names are canonical, and the tracker's label strings may differ only through the mapping you were given.

Transitions: unlabeled goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` when the reporter replies. The maintainer can override at any time; flag a transition that looks unusual and ask before taking it. Every one of the six roles is an exit from here, so a triaged item always lands in a named state.

### A PR is an issue with attached code

When the repo treats external pull requests as a request surface (see `docs/agents/issue-tracker.md`, which also defines who counts as external and how a bare `#42` resolves), PRs use the same roles, states, and machine. Deltas:

- `ready-for-agent`: a brief is attached and an agent takes the next step on the diff — finish it, close gaps, answer review points.
- `ready-for-human`: it is ready for a human to merge.
- Discovery surfaces only *external* PRs, so a collaborator's in-flight PR is not triage work. The filter is discovery-only: a named PR is always triaged, whoever wrote it.

## Reference

## [YOU] Phase 1: Survey

Query the tracker and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

Include external PRs when they are in scope, tagging each line `[PR]` or `[issue]`. Show counts plus a one-line summary per item and let the maintainer pick.

**Done**: all three buckets queried, every item shown with its age and a one-line summary, and every PR line tagged — or the survey is empty and you said so.

## [YOU] Phase 2: Gather context

Read the full issue or PR: body, comments, labels, author, dates, and for a PR the diff. Parse prior triage notes first and check whether the reporter answered the open questions; present the updated picture before continuing, and never re-ask what is resolved — a reporter who answers twice and still waits stops answering.

Explore the codebase through the project's domain glossary, and respect the ADRs in the area. Then run two checks, following [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md):

- **Redundancy**: search for an existing implementation of the behaviour *by domain concept*, not by the request's wording, and report where you looked. Found it, and the outcome is an already-implemented `wontfix` (Phase 6).
- **Prior rejection**: read every `.out-of-scope/*.md` and surface any file resembling this request, quoting the recorded reason.

**Done**: the item read in full, prior notes parsed with each open question marked answered or still open, and both checks answered with the searches that produced them named.

## [YOU] Phase 3: Recommend

Give the maintainer your category and state with reasoning, plus a short codebase summary relevant to the request — including whether it is already implemented. Then wait for direction.

**Done**: the recommendation states one category, one state, and the evidence behind each, and the maintainer has answered with a direction or a follow-up you have answered.

## [YOU] Phase 4: Verify the claim

Check the claim before grilling it. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims: check it out, run the relevant tests or commands. Report one of three verdicts: **confirmed** (with the code path), **failed**, or **insufficient detail** (a strong `needs-info` signal). A confirmed verification makes a far stronger brief, because the agent inherits a reproduction instead of a description.

**Done**: a verdict is reported with its evidence — a command and its output, a code path, or the exact detail the reporter left out.

## [YOU] Phase 5: Grill

Only when the request still needs fleshing out. Call the Skill tool twice, for "grilling" and "domain-modeling", then grill one round of questions at a time, sharpening domain terms and updating `CONTEXT.md` and the ADRs inline as decisions land.

**Done**: every question from the grilling is answered in the notes or recorded as a decision in `CONTEXT.md` or an ADR.

## [YOU] Phase 6: Apply the outcome

- `ready-for-agent`: post an agent brief following [AGENT-BRIEF.md](AGENT-BRIEF.md).
- `ready-for-human`: same structure, plus why it cannot be delegated — judgment calls, external access, design decisions, manual testing.
- `needs-info`: post triage notes with the template below.
- `wontfix`: close it, and pick the comment by *why*:
  - **Already implemented**: point at where it lives. Write nothing to `.out-of-scope/` — that base records rejections, and a built feature filed there poisons every later dedup check.
  - **Rejected, bug**: a polite explanation, then close.
  - **Rejected, enhancement**: write to `.out-of-scope/`, link the file from a comment, then close, following [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md).
- `needs-triage`: apply the role, with an optional comment if there is partial progress worth keeping.

**Done**: the item carries one category and one state role, the comment matching that state is posted, every posted text opens with the disclaimer line, and a closed item links either the code that already does it or the `.out-of-scope/` file that explains why not.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Everything resolved during grilling goes under "established so far", so the work survives a quiet thread. Questions must be specific and actionable — "please provide more info" wastes a round trip.
